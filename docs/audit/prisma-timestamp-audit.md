> Generated by `scripts/audit_prisma_timestamps.py` as part of Step 7
> of the date/time accuracy fix. Does NOT modify `schema.prisma` —
> migration requires explicit user approval per the spec.

## Summary

- **Total DateTime fields**: 363
- **@db.Timestamptz** (correct — timezone-aware): 135
- **@db.Timestamp** (plain timestamp — FLAG): 0
- **Plain DateTime** (no `@db` → defaults to `timestamp(3)` in PostgreSQL — FLAG): 228

## Verdict

**228 of 363 DateTime fields (62.8%) are stored as plain `timestamp` (without timezone) in PostgreSQL.**

Plain `timestamp` stores the wall-clock reading verbatim, with no
timezone metadata. When the server timezone differs from the
client timezone (or when Daylight Saving Time shifts), reads and
writes can drift. For the Daxelo-Kinrel family-base app, where
IST (UTC+5:30) is the implicit reference timezone but the
server runs in UTC, this means:

- A `createdAt` written via Prisma `@default(now())` is stored as
  the server-local (UTC) wall-clock — but reading it back as a
  `Date` object gives the same UTC instant, so this works
  _only_ because the server runs in UTC consistently. If the
  server timezone ever changes (e.g., a deploy in a non-UTC
  region), all historical timestamps would be misinterpreted.
- A user-entered deadline (e.g., Truth Streak `deadline`) written
  via the client is the client-local wall-clock — the server
  stores it verbatim with no timezone info, so a viewer in
  another timezone sees a different wall-clock reading.

## Recommendation

Migrate all plain `DateTime` fields to `@db.Timestamptz` in a
single Prisma migration. The migration requires:

1. Adding `@db.Timestamptz` to each plain `DateTime` field in
   `schema.prisma`.
2. Running `prisma migrate dev --name add_timestamptz_to_*`.
3. The generated SQL migration will `ALTER TABLE ... ALTER COLUMN
   ... TYPE timestamptz USING ... AT TIME ZONE 'UTC'` (or
   similar) — for columns already storing UTC values, this is
   a no-op semantically but enables correct timezone handling
   going forward.
4. For user-entered deadlines (Truth Streak, decision deadlines,
   etc.), audit each value to determine if it should be
   reinterpreted as IST before the migration.

This migration is intentionally NOT done in Step 7 — it requires
user approval per the spec.
